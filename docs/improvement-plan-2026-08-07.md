## 0. Dependency decision (stated once)

**Add exactly two packages. Both ship inside the Expo Go binary — no prebuild, no dev client, no native config.**

| Package | Why it earns its place |
|---|---|
| **`expo-haptics`** | The Qibla lock-on, the 15° turn tick, and any future tasbih counter have no other channel. A compass you must *look at* to use is a broken compass. Tiny, one API call, `Platform.OS !== "web"` guard required (it throws `UnavailabilityError` on web, it does not silently no-op). Ships with a `hapticFeedback` toggle in settings — a phone that buzzes in a masjid needs an off switch. |
| **`react-native-svg`** | The only dependency that unlocks **arcs**, and the Qibla redesign rests on four of them: the 72-tick graduated bezel as one `<Circle strokeDasharray>` node instead of 72 views, the ±5° capture wedge, the closing confirmation ring (`strokeDashoffset`), and a real balanced needle `<Polygon>` with a counterweight tail instead of the current CSS-border triangle-on-rectangle seam. It also supersedes `expo-linear-gradient` (`<Defs><LinearGradient>`) and later gives the prayer screen a progress ring for free. |

**Explicitly rejected:**

- **`react-native-reanimated` / `react-native-gesture-handler`** — core `Animated` + `PanResponder` already carry the sheet and will carry the dial natively (transform + opacity are the native-drivable families; that is all this app animates). Migration cost is high, payoff is zero.
- **`expo-linear-gradient`, `expo-blur`, `expo-image`, `moti`** — nothing in the design needs them once SVG is in.
- **A bundled typeface (Inter or otherwise).** The numerals argument that justified it is false: `ReactTypefaceUtils` maps `"tabular-nums"` to the `tnum` feature and Roboto ships it, so **every missing tabular-nums site is fixable today with zero assets**. And RN cannot select a weight off a variable font's axis on either platform — you would ship four static families and convert every `fontWeight` in the app to a `fontFamily` swap. That is a large project for a taste outcome. Drop the inert `"expo-font"` **plugin entry** from `app.json:25`; never uninstall the **package** (`@expo/vector-icons` depends on it).
- **`@bacons/apple-targets` / true widgets** — ends Expo Go support. Out of scope.
- **eslint + @typescript-eslint** — two proposals wanted lint guards (`no-restricted-syntax` on raw `fontSize`/hex literals). There is no eslint in `package.json` and no config in the repo. Worth doing, but it is its own ticket with its own devDeps; do not smuggle it into a colour fix.

**New assets (not dependencies):** `adaptive-icon.png`, `adaptive-icon-mono.png`, `notification-icon.png`. Generate them by extending `scripts/gen-app-icons.js`, which already holds the mosque glyph in unit coordinates and a dependency-free PNG encoder. `makeIcon()` hardcodes alpha 255, so it needs an alpha path.

## 1. QIBLA — the redesign (headline)

**Design direction, in one sentence:** stop asking the user to read a sentence to know where to point the phone; make the instrument itself close the loop — a graduated dial that carries absolute orientation and the sun cross-check, a **fixed gate at 12 o'clock** the Kaaba mark must be brought into, a **linear turn tape** underneath that gives 2× the angular resolution of the rim for the last few degrees, and an alignment that is **earned** — a ring closes, the needle grows, the phone taps once.

Everything below is `app/qibla.tsx` unless stated.

### Q1 — One native Animated value, unwrapped heading, shortest-arc fix

The whole screen currently has zero animation: `rotation` is plain React state (`:233`) and `spin()` (`:266`) rebuilds a fresh transform array for **fourteen** absolutely-positioned full-size `rotor` layers on every render, gated at 0.5° (`:153`) so the dial visibly steps.

**Prerequisite imports:** `Animated` and `Easing` are *not* currently imported (`:2-8`). Add both from `react-native`.

**The shortest-arc fix.** `smoothAngle` normalises to 0–360 (`qibla.ts:45-47`), so `smoothed.current` jumps 359 → 1. Interpolate that directly and the dial spins 358° the wrong way every time the user crosses north. Keep `smoothed.current` exactly as it is, and maintain a second, deliberately **unbounded** accumulator alongside it:

```ts
const spinAnim = useRef(new Animated.Value(0)).current;
const unwrapped = useRef(0);          // allowed to drift past 360 and below 0
const lastAnimatedTo = useRef(0);
// inside the watchHeadingAsync callback, after `smoothed.current = next`:
unwrapped.current += angleDelta(prev, next);   // angleDelta is qibla.ts:37, returns -180..180
```

`angleDelta` makes 359 → 1 read as **+2°**, never −358°. That is the entire fix.

**Do not `.start()` on every sample.** `watchHeadingAsync` fires at 10–60 Hz and each native `.start()` is a bridge round-trip (`createAnimatedNode` + `startAnimatingNode`). Gate it — accumulate on every sample, animate only when it matters:

```ts
if (Math.abs(unwrapped.current - lastAnimatedTo.current) > 0.25) {
  lastAnimatedTo.current = unwrapped.current;
  Animated.timing(spinAnim, {
    toValue: unwrapped.current,
    duration: reduceMotion ? 0 : 140,
    easing: Easing.out(Easing.quad),
    useNativeDriver: Platform.OS !== "web",   // RNW has no native animated module and warns
  }).start();
}
```

**Collapse fourteen rotors into one.** A single `Animated.View` (`styles.face`, full dial size) carries:

```ts
transform: [{ rotate: spinAnim.interpolate({ inputRange: [0, 360], outputRange: ["0deg", "-360deg"] }) }]
```

Leave `extrapolate` at its default `"extend"` — that is what makes the unbounded accumulator work with no wrap logic in the view layer. Every world-fixed child becomes a **static** `View`/`Text` inside `face` with a fixed `transform: [{ rotate: \`${angle}deg\` }]`. Keep those children full-size and absolutely positioned (`width/height: DIAL`, `position: "absolute"`) so their transform origin stays the dial centre; only then does the parent's animated rotate compose correctly.

**Six glyphs must stay upright**, not five: N, E, S, W (`:301-309`), the sun (`:320-327`) and the Kaaba (`:336-343`). Each becomes `Animated.Text` with:

```ts
transform: [
  { rotate: `${-angle}deg` },
  { rotate: spinAnim.interpolate({ inputRange: [0, 360], outputRange: ["0deg", "360deg"] }) },
]
```

Rotations about a shared origin commute, so the order of the static and animated entries does not matter. The sun's angle (`sunNow.sun.azimuth`) and the needle's `bearing` are **not** constants — memoise those two interpolations on their values.

**Stop feeding heading into state for the dial.** Keep `setHeading` only for the guidance text and the accuracy verdict, and raise its threshold from 0.5° to *"the rounded turn changed"* — `Math.round(angleDelta(next, bearing))`. Per-frame cost falls from 14 JS-computed transforms to one native one, and re-renders drop by roughly an order of magnitude.

Honour `AccessibilityInfo.isReduceMotionEnabled()` + its `reduceMotionChanged` listener (see **N3**) by setting `duration: 0` — the dial still tracks, it just does not sweep.

### Q2 — Fixed index gate at 12 o'clock

The needle *does* land at 12 o'clock when aligned (`spin(bearing)` = `bearing - rotation`), but **nothing on screen marks 12 o'clock as the target** (`:274-349`). The user is handed a floating arrow and left to infer that "up" is the goal.

Add a fixed index **outside** the ring at 12 o'clock that does not rotate: a 14px downward chevron in `colors.text`, flanked by two short `colors.border` gate posts at ±5° so the capture window is visible **before** you reach it. With SVG the wedge between them is a `<Path>` arc at `colors.accent` / 0.12 opacity. The task becomes "bring the Kaaba mark into the gate" — self-evident, closed-loop, no reading required.

### Q3 — Linear turn tape (the precision instrument)

At 288px diameter the rim travels ~2.5px per degree, so the final 5° — precisely where alignment is decided (`ALIGNED_TOLERANCE_DEG = 5`, `qibla.ts:87`) — are effectively invisible. Replace the 22px instruction line (`:351-361`) with a turn tape.

- `const TAPE_W = Math.min(320, windowWidth - 2 * spacing.l)` — **do not hardcode 320**: `content` has `padding: spacing.l` on both sides (`:429`), so a 360px phone leaves 328px.
- Container `{ width: TAPE_W, height: 44, overflow: "hidden" }`, a fixed 2px `colors.text` index at its centre.
- Inside, an `Animated.View` with 5° graduations across ±60°, translated by
  `turnAnim.interpolate({ inputRange: [-60, 60], outputRange: [TAPE_W * 0.994, -TAPE_W * 0.994], extrapolate: "clamp" })`
  → ~5.3 px/deg, **2.1× the rim's resolution**. The last 3° finally read.
- Drive `turnAnim` from `angleDelta(smoothed.current, bearing)` **inside the watchHeading callback** — not from the rendered `guidance.turn`, which Q1 deliberately throttles to 1° granularity and would step the tape in 5.3px jumps. Its own `Animated.timing(…, { duration: 140, useNativeDriver: Platform.OS !== "web" })`, kept separate from the dial's unwrapped value: `turn` folds at ±180, but that discontinuity always sits outside the clamped ±60 window.
- **No fake fade.** Two `colors.surface` overlay views would read as a hard clip identical to `overflow:"hidden"` alone (`colors.surface` *is* the screen background, `:426`). Either accept the hard edge or take a real `<LinearGradient>` from SVG.

Net: the circle carries absolute orientation and the sun cross-check (which needs a full 360° view); the tape carries the turn-left/turn-right HUD precision.

### Q4 — Rebuild the dial face (SVG)

The face is 8 minor ticks at 30° spacing (`:36`) plus 4 letters — twelve marks around a 288px circle. That is decoration, not graduation.

- **Bezel:** `<Circle r={DIAL/2 - 6} fill="none" strokeWidth={10} strokeDasharray={[1.5, (2*Math.PI*r)/72 - 1.5]} />` → 72 perfectly even 5° ticks, one node. A second `<Circle fill="none">` on a 30° dash period for majors. **`<Circle>` defaults to `fill="black"` in react-native-svg** — every tick circle needs explicit `fill="none"` or you get a solid disc.
- **Needle:** `<Polygon points="0,-120 7,-92 3,52 -3,52 -7,-92" />` — head *plus a short tail crossing the hub*, so it reads as a balanced needle rather than an arrow sticker. (A points list with every vertex above the origin is a floating diamond — the exact failure the current `arrowHead`/`arrowStem` seam has.)
- Cardinals at 11px/700, 1.2 letterSpacing, `colors.textSecondary` (N in `colors.text`); degree numerals only every 90° — denser is noise at this diameter.
- **Kaaba mark:** keep the emoji. MaterialCommunityIcons has no Kaaba glyph — I confirmed `mosque`, `mosque-outline` and `star-crescent` exist but none is a Kaaba, and `mosque` is a domed mosque, the wrong building. Pin it: wrap in a fixed 24×24 centred View, `fontSize: 20, lineHeight: 24, includeFontPadding: false`, and **document in a comment why this one stays emoji** so a future icon sweep does not "fix" it.
- **The `☀️` at `:326` goes.** Replace with `<MaterialCommunityIcons name="white-balance-sunny" size={16} color={colors.attention} />` — a 14px colour emoji on a rotating element is an illegible smear on Android and cannot take a theme colour. Carry `marginTop: 26` and `opacity: 0.9` onto the icon's `style` prop; that 26 is what places it on the rim rather than the dial's top edge.

**If SVG is refused** there is a real but plainer fallback: RN 0.81 supports the `transformOrigin` style prop, so each tick can be a 1.5×8 View (`position:"absolute", top:6, left:DIAL/2-0.75, transformOrigin:[0.75, DIAL/2-6]`) — 72 tiny nodes instead of 72 full-size layers. Arcs and the closing ring are simply not achievable that way; the lock-on degrades to colour + scale.

### Q5 — Alignment as an earned event

Alignment currently changes three things, all instant and all colour-only: the dial border (`:275→453`), the hub fill (`:348→522`), the instruction colour (`:353→531`). A colour-blind user learns they are aligned only by reading a sentence.

- **Haptic**, rising edge only: `Haptics.notificationAsync(Success)`, guarded by `const wasAligned = useRef(false)` **with hysteresis** — enter at `|turn| <= 5`, leave only at `|turn| > 8`, or it buzzes continuously while the user hovers on the boundary. Keep the 8° exit in a local ref; `qiblaGuidance` hardcodes `ALIGNED_TOLERANCE_DEG` (`qibla.ts:104`) and the visible text still flips at 5°, which is correct. Gate on `quality.trustworthy` — the phone must never celebrate a reading the app itself does not believe (`aligned` at `:247` already ANDs it in). Wrap in `Platform.OS !== "web"`. Add a light `impactAsync` on each 15° bucket change, same trustworthy gate.
- **Visual lock-on:** `const lock = useRef(new Animated.Value(0))`, `Animated.timing(lock, { toValue: aligned ? 1 : 0, duration: 260, easing: Easing.out(Easing.cubic), useNativeDriver: Platform.OS !== "web" })` → needle `scale` 1 → 1.06, gate `opacity` 0.35 → 1.
- **Closing ring** (SVG): `Animated.createAnimatedComponent(Circle)` with `strokeDashoffset` running `C → 0` so a ring visibly *closes*. `strokeDashoffset` is **not** native-drivable → `useNativeDriver: false`, and therefore it **must live on a separate Animated node** from the native-driven needle scale, or RN throws *"Attempting to run JS driven animation on an animated node that has been moved to native"*. This is the constraint that bites mid-build; design around it up front.
- **Idle pulse** only while aligned: `Animated.loop` of a 1100ms sequence → halo opacity 0.25 → 0.6. Stop the instant alignment is lost; never start under reduce-motion.
- **Shape, not just hue:** on alignment the hero collapses to `Facing the qibla` beside a `check-circle` icon.

### Q6 — Type hierarchy, colour correctness, dark-mode depth

**Hero.** The largest text is currently a 22px instruction while everything factual is crushed into one 14px run-on line: `Qibla 119° ESE · 4,780 km · Compass ±5°` (`:363-367`). Adopt the pattern `prayer.tsx:318-329` already established: 13px/600 uppercase kicker (0.6 letterSpacing) over a large title.

- Kicker `TURN RIGHT` in `colors.textSecondary`; hero `24` at 44px/700, `fontVariant: ["tabular-nums"]`, `letterSpacing: -1`. The word carries meaning, the number carries precision, and they stop competing.
- Replace the run-on with a three-column strip (`row`, `space-between`, hairline dividers): `BEARING / 119° ESE` · `TO MAKKAH / 4,780 km` · `COMPASS / ±5°`. Kickers 10px/600 uppercase; values 15px/600 tabular. When `accuracyLabel` is null render **`No compass`** if `heading.kind !== "live"` (it is permanently null on web, `:248-251`) and an em dash only for the live-but-unreported case — never drop the column, or the strip reflows.

**Colour.** `NEEDLE_COLOR = placeTypeColors.masjid` (`:33`) pins the needle to `#2E7D57` and bypasses the palette — the exact thing `theme.ts:1-4` prohibits. On the dark dial well (`colors.canvas` `#201F1D`) that green measures ~3.3:1; `colors.accent` `#6FC59B` measures ~8.0:1. **Replace at all five call sites** — `dialAligned` (`:454`), `arrowHead` (`:501`), `arrowStem` (`:507`), `hubAligned` (`:523`), `instructionAligned` (`:532`) — then delete the constant so it can never be bypassed again.

**Depth.** `shadowColor: "#000"` on the `#141312` screen background (`:447-451`) is mathematically invisible, so in dark mode the dial flattens into the page. Branch on `scheme` — light keeps a softer, lower shadow (`0.06 / 18 / (0,8)`, `elevation: 3`); dark drops the shadow entirely and expresses lift **by luminance**: the well in `colors.canvas` on the `colors.surface` screen, ringed by 1px `colors.surfaceSecondary` reading as a lit top edge. Same for ticks: `colors.border` `#3A3835` on `#201F1D` is nearly invisible, so in dark mode draw minors in `colors.textSecondary` @ 0.45 opacity, majors at full.

**Plumbing this needs, and it is not optional:** `useStyles` destructures only `colors` (`:61-64, :68`). Change to `createStyles(colors, scheme, dial)` with `useMemo(..., [colors, scheme, dial])` and `const { colors, scheme } = useTheme()`. **Do not** shortcut by comparing against an imported `darkColors` — that is the direct-palette import `theme.ts:1-4` forbids. While there, make the dial responsive: `const DIAL = Math.min(320, windowWidth - 2 * spacing.l)`, and derive the stem height as `DIAL/2 - 62 * (DIAL/288)` rather than the hardcoded `DIAL_SIZE / 2 - 62` (`:506`). Note `app.json:12` sets `supportsTablet: false`, so this is for Android tablets, foldables, web and 360px phones — not iPad.

### Q7 — States: no-compass/web, and the sun card

**No-compass is a first-class state, not an edge case.** `const rotation = liveHeading ?? 0;` (`:233`) means that on web, with location denied, or on a device reporting no heading, the dial renders **exactly as if the user were facing due north** — N at 12 o'clock, full-accent needle at the bearing, same hub, same shadow. A user picks up the phone, turns, watches a needle that does not move, and concludes the direction under it is correct. **Branch the hero; do not reuse the instrument:**

- Render a distinct north-up **diagram**: no shadow, needle in `colors.textSecondary`, an explicit `NORTH-UP DIAGRAM` kicker, a fixed up-arrow `N`, and **no gate, no tape, no animation, no alignment claim**. (Avoid `borderStyle: "dashed"` + `borderRadius` — unreliable on Android. With SVG use a true `strokeDasharray` ring.)
- **Promote the bearing to the hero:** `119` at 44px/700 tabular with `EAST-SOUTH-EAST` as the kicker. In this state the number *is* the deliverable. Allow two lines or it wraps at 360px.
- Move `heading.reason` (`:117, :125, :173`) directly beneath the hero and **give each reason an action**: denied → a "Allow location" button re-running `requestForegroundPermissionsAsync()`, falling back to `Linking.openSettings()` once the OS stops prompting; web → "Works with any compass app — or use the sun, below."
- Render the sun card **expanded and immediately beneath the hero** in this state; on web it is the only functioning technique, and today it sits below three stacked note cards.
- **`usingFallback` is independent of `heading.kind`.** If permission is granted but `getCurrentPositionAsync` throws, the catch at `:105-108` leaves `fellBack = true` while `granted` stays true — the compass goes live with a London-fallback bearing. Keep the fallback as its own compact line that renders in **both** states; fold it into the kicker only when `heading.kind === "static" && usingFallback`.

**Sun card vs. interference warning.** `noteAttention` (`:547`) and `sunCard` (`:556`) use the **identical** `attentionSoft` background and `attention` border — so the app's only genuine alarm ("something magnetic is nearby, the heading is wrong") is visually indistinguishable from an explainer that is on screen 100% of the time.

- Reserve orange **strictly** for the compass-quality warning. Re-skin the sun card neutral: `colors.canvas`, 1px `colors.border`, with the `weather-sunny` icon in `colors.attention` as the only warm note. Split the `"☀️  Check it against the sun"` title (`:395`) into an icon + `<Text>` row with `gap: spacing.s` — the two literal spaces faking a gap measure differently on each platform.
- **Progressive disclosure.** Collapsed by default: one line at 15px/600 plus a `chevron-down`. Expanded: the calculated-not-sensed rationale and the shadow-crossing time from `qiblaSunCrossings` (`qibla.ts:231`) — the most delightful fact on the screen, and it deserves to be a reward rather than wallpaper. Animate with a measured height (`onLayout` → `Animated.timing(h, …, { useNativeDriver: false })` + `overflow:"hidden"`); **prefer this over `LayoutAnimation`**, which is only partially supported under the New Architecture (`newArchEnabled: true`).
- **Collapsed copy must branch on daylight.** `sunNow.instruction` is *"The sun is too low to use right now"* whenever `altitude <= 5` (`qibla.ts:200-203`) — a British winter afternoon. When `!sunNow.sunUp`, show `crossings.towards` as *"Sun sits on the qibla line at HH:MM"* if it exists, else *"Available in daylight"*.
- **Make prominence state-driven.** Auto-expand and hoist the card **above** the metrics strip whenever `!quality.trustworthy || heading.kind === "static"`. When the magnetometer is compromised the sun method is not a footnote, it is the answer — and today it sits *below* the very warning that makes it relevant. Simultaneously **de-authorise the dial** in that state: needle to `colors.textSecondary`, gate to 0.35 opacity. Right now an interfered compass still renders a confident full-accent needle even though `:247` has already decided the reading is untrustworthy.
- Fold the tips block (`:408-417`) into a second collapsed row — most of it is delivered better and contextually by `assessCompass`, which says "Hold the phone flat and level" only when the phone is actually tilted. Keep only the privacy sentence, promoted to a standalone 12px footnote.

### Q8 — Qibla accessibility

The dial is `accessible` + `accessibilityRole="image"` with a label that recomputes on every heading update (`:274-283`) — but a label is only announced when focus **lands**; neither VoiceOver nor TalkBack re-reads a focused element because a prop changed. A blind user turning on the spot hears the instruction once, then silence. The screen's entire purpose is unusable non-visually.

Invert it: **remove `accessible` from the dial** (`accessibilityElementsHidden` hides an element's *children*, not itself — the `accessible` prop at `:276` must go too) and promote the instruction/hero to the single announced element with `accessibilityLiveRegion="polite"` and a label concatenating the instruction, `Math.round(bearing)`, `compassPoint(bearing)` **and `quality.advice`** — the least-trustworthy readings are currently announced with the same confidence as good ones. `accessibilityLiveRegion` is **Android-only** (`ViewAccessibility.d.ts:241`), so the iOS path is a throttled `AccessibilityInfo.announceForAccessibility` in a `useEffect` keyed on a **coarse bucket** (`Math.round(turn / 15)` + the `aligned` boolean), guarded by `isScreenReaderEnabled()` — roughly every 15°, not 20×/second. Announce `"Facing the qibla"` on the rising edge.

Also set `allowFontScaling={false}` on the four cardinal letters and the two glyphs — graphical labels inside a fixed instrument is the sanctioned use of that prop, and the numeric readout and instruction stay fully scalable so no information is lost.

## 3. ANDROID ↔ IPHONE PARITY DEFECTS (explicitly flagged)

These are the tickets where the two builds genuinely differ. Several appear above; consolidated here because parity is an explicit user goal.

**P1 — The collapsed bottom sheet clips the times bar by a different amount on every device.** `BottomSheet.tsx:41-49` computes snaps from `useWindowDimensions().height` — the full **screen** height — but the sheet is absolutely positioned inside a content view the native stack lays out *below* the status bar and header. Every snap is off by `insets.top + headerHeight`, differently per platform: usable content at `peek` is ~36pt on a notched iPhone, ~75pt on an SE, ~59dp on typical Android, ~35dp on a tall-punch-hole Android. The times bar inside is ~79pt on its own, so **on every device the collapsed sheet clips the app's headline feature, by a different amount on iOS vs Android.**
- Fix with `onLayout` on a wrapping View inside BottomSheet: `H = e.nativeEvent.layout.height`, falling back to `windowHeight` for the first frame.
- **Do not use `useHeaderHeight()`.** `getDefaultHeaderHeight.js` returns `headerHeight + statusBarHeight`, so `windowHeight - insets.top - useHeaderHeight()` double-subtracts ~59pt on a notched iPhone and makes things *worse*; and that same file hardcodes `headerHeight = 64` for Android while react-native-screens renders a real 56dp toolbar.
- `peek = H - (PEEK_CONTENT_HEIGHT + insets.bottom)` — the `+insets.bottom` is required because `styles.body` already pads by it. `PEEK_CONTENT_HEIGHT ≈ 124` for the current 29pt handle; **132 if you also widen the handle** (P3). Keep the existing `Math.max(…, 56)` floor on `full` — 56 is what keeps the expanded sheet clear of the Android header.
- Verify: the whole progress track under the countdown visible at rest on a notched iPhone **and** a Pixel.

**P2 — Google Maps' own chrome fights the app's, on Android only.** `PlacesMap.native.tsx:232-240` leaves every Google default on: the "my location" FAB lands under the search row and duplicates the app's own recenter button; `toolbarEnabled` pops two Google buttons over the bottom sheet on every pin tap; `moveOnMarkerPress` nudges the camera on pin tap, firing `onRegionChangeComplete` and re-running `buildPinGroups` — **the exact callout-relabelling churn the slot-pool comment at `:218-223` was written to prevent, and it happens only on Android**; and with no `mapPadding` the Google logo and Terms attribution (which Google's SDK terms require to stay visible) sit permanently under the sheet. Add `toolbarEnabled={false}`, `showsMyLocationButton={false}`, `moveOnMarkerPress={false}`, `mapPadding={{…, bottom: peekHeight}}`. The first three are inert on Apple Maps; **`mapPadding` is supported on iOS** and *does* apply — desirable (it lifts Apple's compass and legal label too) but it changes iOS camera framing, so verify the recenter animation on both. Pass the peek height down as a prop from index.tsx so it cannot drift from P1's constant.

**P3 — Android back button exits the app from a full-height sheet.** `FilterSheet` and `SuggestionSheet` both register a `BackHandler`; `BottomSheet` does not. Dragged to `full` it covers the entire map, yet Android back pops the screen — and index is the root route, so **it exits the app**. Every Material sheet collapses first. Register `BackHandler.addEventListener('hardwareBackPress', …)` returning `true` and springing to `half` when `topValue.current` is nearer `full` than `half`, `false` otherwise. **Read `topValue.current` directly** — it is already kept in sync by the listener at `:56-61`; adding state would force a re-render per animation frame. **Do not guard with `Platform.OS === "android"`** — BackHandler is a documented no-op on iOS/web and both existing sheets register it unguarded; a branch here just makes the three sheets inconsistent. Same ticket: the drag target is 29pt (both HIGs want 44/48) — raise `handleArea` padding to `spacing.l` and add `hitSlop`, or move `panHandlers` up to wrap the handle **and** the times bar. The times bar's own `onPress` still wins for taps: `onStartShouldSetPanResponder` returns true unconditionally so the deepest responder wins the *start* negotiation, and the parent only takes over via `onMoveShouldSetPanResponder` once `|dy| > 4`. Keep `onPanResponderTerminationRequest: () => false`. **Ship only alongside P1** — the extra padding costs 8pt of already-clipped content.

**P4 — The app's own notification channel is dead.** `NotificationsContext.tsx:311-318` creates a `prayer-times` channel at HIGH importance with a sound; the ~60 notifications scheduled at `:223-234` never reference it. **Correct the diagnosis before writing any copy:** expo's fallback channel is created at `IMPORTANCE_HIGH` with vibration (`BaseNotificationBuilder.kt:113-121`), so prayer alerts **do** get a heads-up banner and sound today — nothing is silently broken for users. The real damage is that Android's per-app settings show a generic "Miscellaneous" channel actually carrying the alerts, plus an inert "Prayer times" channel the user can toggle to no effect. Add `channelId: "prayer-times"` to the trigger at `:230` and the dev `sendTest` at `:344` (ignored on iOS, no Platform branch needed), and move `setNotificationChannelAsync` out of `enable()` into `getNotifier()` behind a Platform check — **awaited inside the promise chain**, because `BaseNotificationBuilder.kt:65-75` logs an error and silently falls back if the channel does not exist at *fire* time. Note: re-asserting will **not** raise importance on an existing channel — Android freezes that at creation.

**P5 — Android launcher and status-bar icons.** `assets/` contains only `icon.png` and `pins/`. No `android.adaptiveIcon`, so Android 8+ wraps the legacy square in a system badge and Android 13 themed icons are unsupported; and `expo-notifications` is **not in the plugins array** (`app.json:23-44`), so Android falls back to the launcher icon as the notification small icon — which Android renders as a pure white alpha silhouette, i.e. **a solid white square in the status bar for every prayer reminder**. Invisible if you only test on iPhone. Add `adaptiveIcon: { foregroundImage, backgroundColor, monochromeImage }` and `["expo-notifications", { icon: "./assets/notification-icon.png", color: "#2E7D57" }]`. **Do not set `backgroundColor: "#2E7D57"` unless the foreground is white** — green on green is invisible; either draw a white glyph on green, or keep a light background (`#F9F8F7`, matching the splash) with the existing green mark. Foreground 1024×1024 with art inside the central 66%; notification icon 96×96 white-on-transparent (any colour is discarded). **Scope honestly: config plugins do not run in Expo Go — none of this is visible until an EAS build.** The notification icon is the only shipped *visual bug* here; sequence it first.

**P6 — The suggestion form's Send button can hide behind the iOS keyboard.** There is no `KeyboardAvoidingView` anywhere in the repo. On Android Expo's default `softwareKeyboardLayoutMode: "resize"` saves it by accident; iOS never resizes the window. **Narrower trigger than originally claimed** — with a short message the form is ~240pt and Send clears the keyboard on an SE. It bites once the input grows enough to hit the `maxHeight: 420` cap, at which point the inner ScrollView's viewport bottom *is* the card bottom, sitting behind the keyboard, and no amount of scrolling can lift the button. Also: `insets.top` is effectively counted twice — the backdrop is `absoluteFillObject` inside a view the stack already places below the header, and the card then adds `marginTop: Math.max(insets.top, spacing.l)` on top. **Dropping the double-count is half the fix.** For the rest, prefer explicit Keyboard events (`keyboardWillChangeFrame` on iOS) computing against `endCoordinates.screenY` and the card's window-space top. The one-line `KeyboardAvoidingView` alternative is incomplete: it computes overlap from parent-relative `layout.y`, so inside a header-offset screen it under-computes by the header height and needs `keyboardVerticalOffset`.

**P7 — RTL: Android flips, iOS never will.** `flexDirection: "row"` flips under `I18nManager.isRTL`; `left`/`right`/`paddingRight`/`textAlign:"right"` do not. `app.json` declares no `locales`, so **iOS never flips; Android's `supportsRtl` defaults to true — so Android users with an Arabic or Urdu system language get half-flipped layouts and iOS users get none of it.** That asymmetry is the only genuinely bad option. Given the UI is English-only with no translation layer: call `I18nManager.allowRTL(false)` **at module scope in `app/_layout.tsx`**, before any component renders — inside a component or effect is too late, it must not be conditional on async state, and on Android it takes effect only after a restart. (If you ever add translations, take the other branch instead and do the `paddingEnd`/`marginStart`/`insetInlineEnd` sweep across the six affected files.)

**P8 — Font-scale clipping reads as Android-only.** Android exposes both a Font size and a Display size slider and pushes to 200%; iOS caps lower unless Larger Accessibility Sizes is on. Fixed geometry that breaks: `place/[id].tsx:624/636/643` `width: 64` around 16px times → `minWidth: 64, flexShrink: 0` + `numberOfLines={1}` (**not** `adjustsFontSizeToFit` — `minimumFontScale` is iOS-only, it is unreliable on Android, and shrinking text defeats the setting the user asked for); `maxFontSizeMultiplier={1.3}` on those cells and on `index.tsx:164-167` `nextLabel`/`nextTime`, which share a fixed-height row with a chevron; `index.tsx:964` `nextBlock: { flexShrink: 1 }` / `upcomingRow: { flexShrink: 0 }`. `FilterSheet.tsx:167` has **no maxHeight and no ScrollView** inside a `flex-end` backdrop — at 200% the card overflows off the *top* and the title, "Clear all" and the first filters become unreachable with no way to scroll: add `maxHeight: "85%"` + an inner ScrollView with **`flexShrink: 1`, not `flex: 1`** (which would strand the Done button at the bottom of an 85%-tall card showing two rows). `settings.tsx:483/487` `aboutRow` puts two Texts in a row with no flex — RN's default `flexShrink` is 0 and the value is a ~200-character sentence, so **it is clipped by `card`'s `overflow: "hidden"` at the default font size**: `flex: 1` / `flex: 2, textAlign: "right"`. The row `minHeight`s are already correct (`prayer.tsx:386`, `settings.tsx:418`, `place/[id].tsx:616`) — nothing to do there.

**X1 — Typography tokens.** `theme.ts` exports `spacing` and `radius` and nothing else. ~90 `fontSize:` declarations across 11 files use 12 distinct values; the "eyebrow" label exists five times at three sizes and two weights. Add a `type` export `satisfies Record<string, TextStyle>` (which preserves the `fontWeight` string literals via contextual typing): `display / title1 / title2 / title3 / body / bodyStrong / callout / subhead / footnote / caption / eyebrow / timeLarge / timeRow / timeSmall`. **`const numeric = { fontVariant: ["tabular-nums"] as const }` will not compile** — `StyleSheetTypes.d.ts:480` declares `fontVariant?: FontVariant[]`, a mutable array; write `satisfies TextStyle` and spread that. Migrate screen by screen (each `createStyles` is isolated). Three mappings in the original sweep are wrong and would change the design: `prayer.tsx:398` rowTime is 16/600 and needs its own `timeRow`, not `timeLarge`; `place/[id].tsx:635/:642` are 16/700 and 16/400 and collapsing both to `timeSmall` erases the deliberate weight contrast between published jamaat and calculated start.

**X2 — Tabular numerals (fold into X1, but it is the visible win).** `fontVariant: ["tabular-nums"]` appears exactly **once** in the app (`prayer.tsx:402`) even though times, countdowns, bearings and distances are the primary content. Missing at `index.tsx:967` (the countdown — the site that ticks every 30s; note `:971` is the next prayer's *clock time*, not the countdown), `index.tsx:989`, `prayer.tsx:325`, `place/[id].tsx:635/:642`, `qibla.tsx:534`. Works on Android today with zero assets. One thing it does not fix: the string also changes *length* at `"59 min"` → `"1 h 0 min"`, so add a `minWidth` to `styles.nextBlock` if that jump matters.

**X3 — Elevation tokens.** Seven hand-rolled shadows with drifting values. Android ignores `shadowOpacity/Radius/Offset` entirely and renders only `elevation`, so the recenter button (0.15, elev 4) and the qibla dial (0.10 but 12px radius, also elev 4) look clearly different on iOS and identical on Android. Export `elevation(scheme, colors)` returning `raised` / `floating` / `sheet` built with `Platform.select({ ios: {...}, android: { elevation }, default: { boxShadow } })` — the web branch also kills react-native-web's per-style-object deprecation warnings. **Scope the dark-mode claim correctly:** five of the seven sites already carry `borderWidth: 1, borderColor: colors.border`, so they are *not* unseparated at night and adding a hairline would fight the existing border. The genuine gaps are exactly two: `BottomSheet.tsx:200-215` (no border, black shadow only, and it uses `colors.surface` which is **darker** than the map beneath it — move to canvas/surfaceSecondary) and `SuggestionSheet.tsx:122-139`.

**X4 — SuggestionSheet / FilterSheet lift.** `SuggestionSheet`'s card declares a 16pt iOS shadow and **no `elevation`**, so it is perfectly flat on Android — the one inconsistent surface in the app. Add `elevation: 8` to the **card** (`:139`; the `elevation: 20` at `:118` is on the backdrop). `FilterSheet`'s card declares neither shadow nor elevation — add the `BottomSheet.tsx:209-213` pairing **plus `borderTopWidth: 1, borderColor: colors.border`**, since Android draws elevation shadows in black and the dark filter sheet would still have no visible edge. (SuggestionSheet already has a border.)

**X5 — Bottom sheet: translateY instead of the `top` layout prop.** The sheet is `position:absolute` with `bottom:0` and an animated `top`, so **both edges are pinned and changing `top` changes the sheet's height every frame** — and `styles.body` is `flex:1`, so the FlatList gets a full Yoga pass plus a VirtualizedList viewport recalculation (which can mount/unmount rows mid-drag) at 60fps. Fix the geometry: `top: snaps.full`, `height: windowHeight - snaps.full` (inline — `snaps` depends on measured height), drop `bottom:0`, interpolate `[snaps.full, snaps.peek] → [0, snaps.peek - snaps.full]`. Height is now constant; zero layout work per frame. That alone is the win and keeps the JS driver. **Converting `aboveSheet` is mandatory, not optional** — it reads the same Animated.Value, and RN throws if one consumer stays JS-driven. To go fully native afterwards, replace `Animated.event` with `onPanResponderMove: (_e, g) => top.setValue(g.dy)` (`setValue` is permitted on a natively-attached node; `Animated.event` + PanResponder cannot use the native driver) — and note `addListener`/`stopAnimation` become async round-trips, so track position as offset+dy in a ref rather than relying on the listener.

**X6 — Sheet feel: velocity handoff and rubber-band. Order strictly after X5.** `settle()` uses velocity to *pick* the snap and then throws it away — `Animated.spring` starts from rest, so a fast flick decelerates to a dead stop at the fingertip and re-accelerates. Pass `velocity: vy * 1000` (PanResponder's `vy` is px/ms, spring config is units/sec). Not on `snapToNeighbour` — that is the accessibility action with no gesture behind it. Replace the hard clamp with a 5:1 compressed overdrag (`inputRange: [full-300, full, peek, peek+300]` → `[full-60, full, peek, peek+60]`) so dragging past a limit gives ~60px of resisted travel instead of a frozen sheet that reads as a dropped gesture. Consider `vy * 160` → `250` (keeping the `clamp` around `projected`); 160ms means a genuine flick often fails to clear the halfway point. **In the current `bottom:0` geometry the 60px of give makes the sheet 60px taller — another full relayout, the exact cost X5 removes.**

**X7 — Sheets appear and vanish in one frame.** `FilterSheet`'s docstring calls it "a slide-up sheet" but `:57` is `if (!visible) return null` — the screen just goes dark instantly, and `SuggestionSheet` is identical. Mounted-while-animating pattern: `mounted` state + an Animated.Value, 220ms `Easing.out(Easing.cubic)` in / 180ms `Easing.in` out, backdrop opacity native-driver-safe, card `translateY` from a measured `onLayout` height cached in a ref with a constant fallback (or the very first open animates from 0 and appears not to move). **Set `pointerEvents={visible ? "auto" : "none"}` on the backdrop** or it eats taps for the whole 180ms exit. For SuggestionSheet use a short fixed `-24` translate + opacity, not a full card-height drop — it is top-anchored and autofocuses its input, so the keyboard rises simultaneously and fights a long slide. Keep the `BackHandler` effects keyed on `visible`, not `mounted`. Do not try to animate `elevation` — not interpolatable on Android.

**X8 — Stack transitions differ per platform by accident.** `_layout.tsx:66-76` never sets `animation`, so every push inherits react-native-screens' platform default and the same tap produces two different navigation metaphors. Set `animation: "slide_from_right"` in `screenOptions`; `reduced ? "fade" : "slide_from_right"` via the N3 hook, read inside `ThemedNavigator` where `useTheme()` already lives (screenOptions is rebuilt per render). `"none"` is jarring enough that a 150ms fade is the better reduced-motion target. `gestureEnabled` is iOS-only for native-stack — harmless, but do not sell it as parity. Do not use `animationDuration`; it is unreliable in both directions.

**X9 — Progress bar off the JS thread.** `index.tsx:1000` is a plain View whose `width` is a percentage string recomputed on render — a layout prop, so it cannot use the native driver, it re-lays-out inside its `overflow:"hidden"` track on every tick, and it is not animated at all. Keep the fill at full width and animate `transform:[{scaleX}]` with `transformOrigin: "left center"` (RN 0.74+; verify visually under `useNativeDriver: true` on Fabric — the dependency-free fallback is centre scaleX plus a compensating `translateX` from `onLayout`). Drop `borderRadius: 2` from `progressFill` — scaling X squashes it to sub-pixel at low progress; let the track's own overflow+radius do the rounding.

**X10 — Countdown ticks at an arbitrary phase.** Both countdowns use a fixed 30s `setInterval` that is not aligned to the minute boundary, so the displayed minute changes at a random phase and can be 30s stale — *"1 min"* sits on screen while the prayer time passes. Replace with a self-correcting `setTimeout` sleeping to `60_000 - (Date.now() % 60_000)`, and add the `AppState` foreground refresh to `prayer.tsx`, which has none (its countdown is silently frozen after any backgrounding). **Do not drop to a 1s cadence for the final hour**: `info` (`index.tsx:113-145`) lists `now` in its deps and runs `computePrayerSchedule` **three times** per recompute — that is three full solar-model runs every second for an hour. Prerequisite: split the memo so the schedule is keyed on location/options/day and only the countdown arithmetic depends on `now`. Then 1s is safe inside the final ~2 minutes only.

**X11 — Place-detail prayer table.** (a) Rename the columns to "Jamaat" / "Time starts" and add a footnote mirroring `prayer.tsx:288-293`: *"Start times calculated on this device · {method} · Asr at {mithl}"* with a link to Settings — nothing on this screen says that column is computed from the user's own settings, even though the Asr row silently changes meaning with the mithl. (b) When `!place.jamaat`, drop the column rather than rendering five em-dashes that read as broken data, and put one honest line above the table. **Per-row dashes still need the `:386` fallback** — `place.jamaat` can exist with individual prayers missing. (c) Promote the unverified-jamaat caution (`:403-410`) — the single most safety-relevant sentence in the product, currently bare 13px text in `colors.attention` with no container — to a bordered `attentionSoft` card with an `alert-outline` icon and the text in `colors.text` (amber-on-amber-soft is the weakest pairing in the palette). Extract `src/components/Callout.tsx` with `tone: "attention" | "info"` **and a `compact` variant** — `index.tsx:728-733` is a deliberately `alignSelf:"flex-start"` map-overlay chip and must not become a full-width card.

**X12 — Facility checklist contradicts PlaceCard's own stated rule.** Each of the six rows encodes the same binary three times (icon colour, label colour, trailing ✓/✕) — 18 signals for 6 questions — and the absent-icon colour is `colors.border`, **1.26:1 on white: not muted, invisible**. `PlaceCard.tsx:27-32` states the product's rule in a comment: icons show only what a place *has*, because "a row of crossed-out absences is noise, and 'not listed' isn't the same as 'not there'". Apply it here: available facilities as accent chips matching the distance pill shape, then one subordinate line *"Not listed: parking, step-free access"*. If the checklist is kept instead, `colors.textSecondary` is 4.3:1 (not 7:1) — fine for a non-text graphic, but `facilityLabelMissing` is *already* textSecondary, so icon and label become identical and the trailing mark must stay. No half-measures.

**X13 — Prayer screen hero and day arc.** The hero's background and border are both `colors.accentSoft`, so the 1px border does literally nothing and the card is a flat tint — and the current-prayer row uses the *same* fill, giving the screen two equally-weighted blocks and no first stop. The countdown is embedded mid-string at the same weight as the words around it, with no tabular-nums. Restructure to eyebrow / baseline-aligned split number / supporting line, on a **solid `colors.accent` card with `colors.canvas` text** (the primary-button pattern) so it outranks the row tint. Differentiate the current row by **shape** — a 3px accent left bar — not a second tint. (The row *is* already marked via `highlightKey`; the accurate gap is elapsed/remaining sense and passed-vs-upcoming, not "no indication of now".) Add a vertical rail with a filled dot per passed prayer. **Prerequisite:** the shared `dayProgress` helper cannot take a single-day schedule — `index.tsx:134-143` depends on the three-day flattened array precisely so the pre-Fajr and post-Isha windows bracket correctly. Signature must be `(prevTime, nextTime, now)` with bracketing left to callers, or do its own ±1-day bracketing internally; `prayer.tsx`'s `getStatus` (`:67-90`) re-derives part of this already and should be absorbed too.

**X14 — Radius scale.** `radius` has only `m: 8` and `l: 12`, so the two sheets agree at 20 **by luck rather than by contract** and the pill — the app's most repeated non-card form — has no name. Extend to `{ xs:4, s:6, m:8, l:12, xl:16, sheet:20, pill:999 }`. Leave the genuine `size/2` circles derived from their size. Two exceptions worth catching in the same pass: `BottomSheet.tsx:223` is `borderRadius: 3` on a 5px handle (half of 5 is 2.5 — arbitrary; use `radius.pill`), and `qibla.tsx:508-509` is `3` on a 6px stem, which **is** width/2 and should be written as such.

**X15 — Directions handoff throws the coordinates away.** `place/[id].tsx:152-165` builds `maps:0,0?q=<name+address>` — a text **search**, not a route — while the app holds verified `lat`/`lng`. For a dataset containing dozens of entries literally called "Prayer Room" that frequently lands on the wrong pin. iOS: `maps://?daddr=<lat>,<lng>&dirflg=w` — **drop `&q=<name>`**; Apple treats `q` as a pin label alongside `ll`, not `daddr`, and combining them is undefined. Android: **default to `geo:<lat>,<lng>?q=<lat>,<lng>(<name>)`**, not `google.navigation:`, which launches turn-by-turn immediately and hard-requires Google Maps — wrong for a 400m walk; keep `google.navigation:` behind an explicit "Navigate" row. Web: `.../dir/?api=1&destination=…&travelmode=walking`. Optional long-press chooser probed with `canOpenURL` needs `ios.infoPlist.LSApplicationQueriesSchemes` (a plist key, still managed workflow, but requires a rebuild). Keep the existing double-catch fallback.

**X16 — Share the app's own summary.** `sharePlace` sends a Google Maps text search, losing every reason the sender used this app. **Ship only the improved text now:** name, address, and a one-line summary built from data already on screen (`PLACE_TYPE_LABELS`, `facilities.sistersSpace`, `jumuahTimes`). **There is no deployed domain anywhere in the repo** — `README.md:186-196` gives generic Netlify instructions with no site name and `public/manifest.json` uses `start_url: "/"` — so `https://<domain>/place/<id>` cannot be written today. When a domain exists, add `ios.associatedDomains` + `android.intentFilters` and the two well-known files, and force `application/json` on `/.well-known/apple-app-site-association` via a Netlify `[[headers]]` block (it has no extension).

**X17 — List row enter animation.** Rows appear and vanish in a single frame on every debounced keystroke, so typing feels like a repaint rather than a filter. Give `PlaceCard` a mount animation (opacity + 8px translateY, native-driver-safe, `delay: Math.min(index * 25, 150)`). **Do not use `LayoutAnimation`** — Fabric support is partial. **Set expectations honestly:** rows that survive a filter keep their key and do not remount, so this fires only for genuinely new rows and does nothing for the common "remove one filter, everything reorders" case, which is what actually looks broken. Hold the delay in a ref computed on first render rather than passing `index` as a prop, or `React.memo` starts failing on every reorder. Note `initialNumToRender={8}` against a 12-row cap puts rows 9-12 on a second, unrelated beat — raise it to `MAX_LIST_RESULTS`. **Leave the other virtualization props alone**; they are harmless and churning working code for no measurable gain is worse.

**X18 — Friday mode.** On the home screen, Jumu'ah-only venues are **actively hidden** unless the user manually enables a filter or types a query (`index.tsx:493`) — so on Friday morning, the single highest-intent moment of the week, the app hides exactly the venues (hired halls, university rooms) the user needs. Fix: on `getDay() === 5`, show a dismissible banner and include `jumuahOnly` rows without requiring the filter. **Drop the proposed filter and re-sort** — `applyFacilityDefaults` forces `jumuah: true` on every masjid (1,942 of 2,244 rows), so filtering on it filters nothing; and only **136 of 2,244** rows have `jumuahTimes`, so "sort by first parseable time, else distance" is just the ordinary distance list. Instead: within the existing distance order, float rows that *have* a `jumuahTimes` value above those that don't, and grey/sink only those whose parsed time has passed. `PlaceCard.tsx:88-99` already renders the times — this is promotion and ordering, not new information. **Scope the change to `listResults`, not `results`**, which also feeds the map at `:717`.

**X19 — Favourites + "my masjid".** No favouriting exists anywhere. Jamaat times — the single most-used number for a regular attendee — take four steps to reach, every day. `FavouritesContext` on AsyncStorage under `favourites:v1` storing **only place ids**, resolved against the live `places` array on render (skeleton row if not yet loaded) so the never-cache-the-dataset rule holds. Heart icon in the detail action row; a favourites section pinned above the distance-sorted rows. **Constraints:** only 157 of 2,244 rows carry a `jamaat` object, so the card must degrade to the calculated start for ~93% of favourites; `NextPrayerBar` computes the next prayer entirely inside its own memo and exposes nothing, so lift that (or add an `onNextPrayer` callback) first; and **render the card in `ListHeaderComponent`, not between the times bar and the list** — the peek budget has no room (see P1).

**X20 — First-run onboarding.** `index.tsx:230` calls `requestForegroundPermissionsAsync()` on mount with no explanation. iOS grants exactly one shot; a cold-start dialog with no context is the classic way to lose the permission permanently, after which every distance and prayer time silently falls back to central London. And the app ships Moonsighting + Hanafi 2-mithl by default with the good explanatory copy locked behind the gear icon — so a Shafi'i user gets a systematically late Asr on every screen and is never told there is a choice. Three dismissible cards gated on `onboarding:v1`: privacy + an explicit Allow button, the Asr mithl choice written through `updateSettings({madhab})` so `touchedKeys` records it as deliberate, and "prayer times and qibla work with no signal". **Corrections:** `getLastKnownPositionAsync` is **not** permission-free, so "keep it unconditional for return users" is a no-op — use the `prayer.tsx:117` pattern (`getForegroundPermissionsAsync()` first; skip the card if granted, show "open Settings" if denied). `OptionRow` is module-local and unexported — extract it before reuse or the copy forks. Gate on the flag having **hydrated**, not on its absence, or first-run users see a flash of the map.

**X21 — Ramadan mode.** `hijri.ts` already knows month 9 and `prayer.tsx:220` already renders the Hijri date, but nothing changes during the highest-traffic month of the year. Add `isRamadan(date)` plus the flanking days, phrased *"Ramadan (approximate — follow your local announcement)"*, never asserted. Swap the prayer hero for an iftar countdown with "Suhoor ends in {remaining}" — lead with remaining time, put the clock time second, since the Fajr row is already on screen. **One notification only:** "Suhoor ends in 30 min". Dropping iftar is deliberate — Maghrib is already announced by the normal plan, and at 7/day the 14-day window inside `MAX_PLANNED = 60` collapses to ~8 days, quietly worsening coverage in the exact month users rely on it most. The imsak-offset toggle needs a home in `PrayerSettings` + `sanitizeSettings`, not local state. Explicitly out of scope: taraweeh times — no schema field, no reliable source; that is a data project.

**X22 — Recent searches.** `searchArea` geocodes on every submit and `clearSearch` throws the resolved origin away, so someone checking the same two places weekly re-geocodes every time and gets "Area search needs a connection" on a bad signal for an area they searched yesterday. Persist the last 5 as `{label, lat, lng}` under `recentSearches:v1`, shown as chips when the input is focused and empty. **Native-only** — `searchArea` returns early on web. Budget the space or render as an overlay: the input lives in `overlayTop`, directly above the map legend. The privacy line is clear and worth stating in the Privacy Centre: these are strings the user typed and coordinates the OS geocoder returned for a public place name — their own search history on their own device, not their GPS trace, and no part of the places dataset. Never store the GPS fix. The Privacy Centre is currently a static read-only `PRIVACY_POINTS.map`, so "Clear search history" means adding an actionable row variant.

## 5. LATER — nice-to-have, large, or speculative

**L1 — Jamaat-time reminders for the favourited masjid** (after X19). `planNotifications` only knows calculated times, but nobody attends the calculated Fajr — they attend the masjid's jamaat. Blockers to resolve first: `NotificationsProvider` wraps `PlacesProvider`, so the notification context cannot call `usePlaces()` — prefer pushing times in via a `reportJamaat()` alongside the existing `reportLocation()` rather than swapping providers, which keeps the plan module pure. `RESCHEDULE_AFTER_MS` only forces a rebuild after **half** the window, so a 3-day jamaat horizon with `WINDOW_DAYS = 6` gives a 3-day staleness threshold that is not tighter than the horizon — jamaat alerts can silently run out. Make `WINDOW_DAYS` a parameter and derive the threshold from it. Dark for ~93% of favourites; say so in the settings copy. And record deliberately that the place **name** and time get written into the OS's on-disk notification store — one user-chosen place is defensible and quite different from caching the dataset, but given the explicit rule this should be a decision, not a side effect.

**L2 — Per-prayer reminder lead times + adhan/silent options.** `minutesBefore: number` → `Record<PrayerKey, number>` (30 before Fajr to wake up, on-time for Maghrib). Requires rewriting the hydration validator (`typeof parsed.minutesBefore === "number"`) with a migration widening an existing number to all five keys, and `prefsFingerprint` must map `PRAYER_KEYS` explicitly rather than stringify the object, or key order changes the fingerprint spuriously. Adhan sound needs a config-plugin `sounds` entry + a second channel — **not available in Expo Go**; gate on `Constants.executionEnvironment === ExecutionEnvironment.StoreClient` (`appOwnership` is deprecated). "Silent (vibrate only)" is **not** free on Android: from API 26 sound is a *channel* property and `content.sound: false` does not silence it — it needs a third channel. It does work per-notification on iOS.

**L3 — Selected-pin state linking list ↔ map.** Tapping a card navigates away without the map ever acknowledging which pin was tapped. Cheapest visible selection without touching the fixed pool (the crash rationale still stands, and `tracksViewChanges={false}` is load-bearing so an Animated marker child is out): swap the slot's `image` to a `-lg` variant added to `PIN_IMAGES` and `gen-pin-assets.js`. **Sequencing:** `mapRef` and the region deltas are private to PlacesMap, so index.tsx cannot drive the camera — pass `selectedId` down and animate in an effect. And "animate 350ms then push" is self-defeating: an immediate push hides the flight, a delayed push makes every tap feel laggy. **The payoff is on the way back** — set the selection, push immediately, and have the map already centred with the pin already enlarged when the user returns. Clear on `clearSearch`/`recenter`, not on a timer.

**L4 — Sunnah and makruh windows.** `deriveWindows(schedule, tomorrowFajr)` returning makruh-after-sunrise / zawal / before-maghrib, duha, last third, midnight — all pure arithmetic over Date objects the app already computes. Render as a collapsible "More times" card, visually subordinate. Flag on the home bar only when currently *inside* one. Copy must be explicit that makruh durations are conventional precautionary margins, not calculated boundaries — the codebase already sets that standard by naming its Zuhr +5 / Maghrib +3 offsets openly. Deliberately not proposed: a "how to pray" reference — scholarly-review risk, different kind of project.

**L5 — Tasbih counter.** Cheapest high-frequency feature available: pure state, no data, no network, works offline and on web. New `app/tasbih.tsx`, entry point from a card at the bottom of `prayer.tsx` (**not** a third header emoji). Persist count and target to AsyncStorage. **Skip the progress ring** — the cited precedent is misread (`qibla.tsx:284-348` spins full-circle rotor layers, it does not draw an arc); a large numeral plus a row of 33 filled/unfilled dots is simpler, more legible mid-dhikr, and matches the app's existing View-and-border vocabulary. Per-tap haptic via the already-added `expo-haptics`, `Platform.OS !== "web"` guarded.

**L6 — Display settings: theme override + high contrast.** `theme` and `highContrast` into `PrayerSettings` + `sanitizeSettings`, plus `highContrastLight/Dark` palettes. **N2 must ship first** — darkening light `textSecondary` is a straight bug fix for every user, not an opt-in. And "a fourth palette is additive, no component needs touching" is false: `place/[id].tsx:43-44` hardcodes `HERO_BACKGROUND`/`HERO_TEXT`, `PlaceCard.tsx:64` reads `placeTypeColors` directly, `_layout.tsx:151` hardcodes white. Route those three through the palette first — and while there, make the hero scheme-aware (`heroSurface`/`heroText`; at night a fully saturated bright green slab on `#141312` is the brightest object in the app, on the screen someone opens before Fajr) and add a `scrim` token so `FilterSheet`'s `rgba(0,0,0,0.4)` and `SuggestionSheet`'s `0.45` stop being two alphas for one role.

**L7 — Android ongoing next-prayer notification.** The in-scope substitute for a widget. A second channel `next-prayer` at `AndroidImportance.LOW`, `sticky: true`, stable identifier so each re-post replaces rather than stacks, presented with a null trigger from the existing foreground path. **The thing that decides whether it is worth building:** an ongoing notification's text is frozen until something re-posts it and there is no background task here to do that — so write the absolute time only (`"Next · Asr 16:42"`) and **drop the relative countdown**, which would read stale for hours. iOS has no managed equivalent; do not promise one.

**L8 — True widgets / Live Activities: out of scope, and say so.** WidgetKit is a Swift app-extension target; an Android widget is an `AppWidgetProvider` in the manifest. Neither can be produced from JavaScript. Doing it means a config plugin writing a native target (`@bacons/apple-targets` or hand-rolled), `expo prebuild`, an EAS build, plus writing the next ~7 days of computed times into App Group UserDefaults / SharedPreferences so native code can render without launching JS. That is privacy-safe and device-local, but it is a week of native work and **a permanent loss of Expo Go testing**. Treat as a deliberate, separately-scoped decision, not a feature ticket.

**L9 — eslint bootstrap.** `no-restricted-syntax` banning raw `fontSize` in `StyleSheet.create` (after X1) and hex/rgba literals outside `theme.ts` and `PlacesMap.native.tsx` (whose `#`-literals are Google Maps JSON stylers, legitimately not app colours). Declares `eslint` + `@typescript-eslint` as new devDeps and needs a config bootstrap — hence its own ticket.
